The app is fundamentally sound on mobile. Correct viewport meta, a real bottom tab bar, generous 314×60 menu rows, no horizontal page scroll on the landing page, pricing, dashboard, exams, stats or results. The matching question uses tap-to-swap rather than drag-and-drop, which is the right call for touch and it works.

Two things are genuinely broken. The exam header is clipped off-screen after every single answer — 10 out of 10 questions, no exceptions. And every friction-telemetry write to Firestore has been failing since the coach_timing event shipped, which is why your Thinking Traps panel is empty. That second one is not a mobile bug; it is losing data everywhere.

Findings

Critical All platforms · silent data loss

Every friction event is rejected by Firestore

question.type is optional and is undefined for ordinary multiple-choice questions. It gets passed straight into the event payload, and Firestore refuses documents containing undefined values. One 10-question session produced 11 consecutive rejections.

FirebaseError: Function addDoc() called with invalid data. Unsupported field value: undefined (found in field meta.questionType) × 11 — one per answered question

The .catch(() => {}) in the service was meant to make this fire-and-forget. It doesn't help: the writes still fail, the errors still surface as uncaught rejections, and you get no telemetry at all. This is the reason your dashboard says “No thinking traps detected yet.”

Fix
web/src/pages/Quiz.tsx:1105 → question.type ?? 'standard'. Better, do it once for everything: strip undefined keys from meta inside FrictionEventService.emit (services/FrictionEventService.ts:58) so no future caller can poison a write.
Critical Mobile only · 10 / 10 reproduction

Exam header is clipped off-screen after every answer

Submitting an answer loads the Coach Breakdown, which forces the app shell to 507px inside a 393px viewport. The parent has overflow-x: hidden, so there is no horizontal scroll — the extra 114px is simply unreachable. What disappears: the exam-name selector, the Q / 10 progress counter, and the theme toggle. The user loses their place in the exam.

shell width 507px viewport 393px clipped 114px horizontal scroll available: none (overflow-x:hidden) elements pushed out: exam selector @ x=406, Q-counter @ x=440 after adding min-w-0: 374px — header restored

Root cause is a Flexbox min-content blowout. div.flex-1 keeps the default min-width:auto, so it refuses to shrink below its content. The content forcing it is the Coach Breakdown header row: emoji, title, and the Quick / Deep toggle on one non-wrapping flex line with px-6 padding — 360px of min-content in 251px of space.

Fix
Safety net, one word: add min-w-0 to the shell div at web/src/App.tsx:329. Verified — it collapses 507 → 374 and the header comes back. Root cause: components/TutorBreakdown.tsx:96, change the header row to flex-wrap gap-2 px-3 sm:px-6.

Across a 100-question mock exam that is real friction, and it compounds with the clipped progress counter above.

High Real device only · predicted, not observed

54 uses of min-h-screen, zero dynamic viewport units

Emulation cannot surface this one, but Android Chrome will. 100vh resolves to the large viewport — the height with the URL bar hidden. Every full-height layout therefore overflows by the URL-bar height whenever that bar is visible, and content jumps as it collapses on scroll. The quiz shell and the app shell both use it.

min-h-screen (100vh) usages: 54 dvh / svh usages: 0
Fix
Swap min-h-screen for min-h-dvh in the layout shells first — App.tsx:325 and pages/Quiz.tsx:1475. Supported in every Android Chrome you care about.
Medium Mobile only

Smart Practice Review traps touch scrolling inside itself

The post-quiz coaching modal puts a fixed 480px scroll window over 3,226px of content, nested inside a page that also scrolls. On touch this is the classic trap: momentum scrolling gets captured by the inner box, and it is not obvious which surface is moving. On a phone the visible text column ends up about four words wide.

inner scroller: 480px window / 3226px content page beneath it: also scrolling
Fix
components/SmartQuizReviewModal.tsx:46 → max-h-none sm:max-h-[30rem], or make the modal full-screen on mobile with a single scroll region.

High Content · not mobile

The Security+ bank is serving project-management questions

Four of the ten questions I was served under CompTIA Security+ (SY0-701) were generic PM scenarios. The Exam Lens then rationalizes them through a security frame, which makes it worse, not better — it reads as confident and it is wrong.

Q1 “During a project kickoff meeting, the project manager identifies a potential risk due to outdated software tools…” → explained via SECURITY TRIAD LENS Q2 “During a project kickoff meeting, the project manager emphasizes the importance of data protection…” Q3 “During a project, a team member discovers a potential security vulnerability…”

Your entire pitch is that you teach how a specific exam thinks. A Security+ candidate who hits a PMP question dressed as security will not file a bug — they will quietly stop trusting the product.

Fix
Audit the Security+ bank for examId mis-tagging. Worth checking whether the other CompTIA banks are contaminated the same way.

What held up

  • Viewport meta is correct, including viewport-fit=cover for notched devices, plus theme-color. Nothing to do here.
  • Matching questions are touch-native. Tap-to-select-then-tap-to-swap, not HTML5 drag. I swapped two definitions with synthetic pointer events and it graded correctly.
  • PBQs are touch-safe by construction. PBQQuestion.tsx is entirely click-driven — no draggable, no drag handlers anywhere in the component.
  • No horizontal page scroll on landing, pricing, dashboard, exams, readiness, or results.
  • Mobile nav is properly built — bottom tab bar plus hamburger, 314×60 menu rows, well over the touch minimum.
  • Full session completes. Ten questions, explanations, matching question, finish, score, coaching review. Nothing hung.

Not tested — and why

  • Login and signup. Both routes redirect to /app while you are authenticated, and I would have had to sign you out to see them. Say the word and I will. This is the path a new phone user actually takes, so it is the biggest gap here.
  • PBQ rendering. Ten Security+ questions produced no type: 'pbq' item. Note that PBQQuestion.tsx contains exactly one responsive class in the whole file — the interaction model is touch-safe, the layout is unverified.
  • Real Android Chrome. This was desktop Chrome at a phone viewport. It does not catch soft-keyboard resize, URL-bar collapse, WebView quirks, or touch latency. The min-h-screen finding above is the one I can predict from source; the rest need a real handset.

Where I could be wrong

  • I nearly filed a false positive. Your Chrome is set to a 20px default font size, which inflates every rem value by 25%. My first measurements showed a 607px blowout. I re-ran the whole thing forced to a real Android 16px root: still 507px, still broken. The bug is real, but it is meaningfully less severe than my first numbers said.
  • My viewport was 374px of content, not 393px — desktop Chrome reserves 19px for a scrollbar that Android overlays instead. That makes every overflow finding conservative, never inflated.
  • I tested as a returning authenticated user with mastery data. The empty-state paths a brand-new signup hits are untested, and that is the cohort your conversion depends on.
  • You cannot currently measure any of this yourself. The friction-event bug means you have zero mobile telemetry. Fix that first — it is the cheapest fix on this page and it is the one that tells you whether the rest of these actually matter to real users.
